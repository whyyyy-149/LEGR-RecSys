# LEGR：LLM-Embedding Guided Retrieval

## —— 语义特征在推荐链路里的价值边界

> **一句话**：LEGR 有两条检索路线——稠密双塔（Recall@50 **10.20%**）和生成式 SID（**8.86%**）——
> 外加一个被证伪的精排假设（受控池 +8.2pp，真实链路 0 增益）。
> **结论：瓶颈和收益都在召回覆盖，精排阶段是冗余的。**

数据：Amazon Reviews 2023 / Musical_Instruments（5-core leave-one-out），57,439 用户 / 24,587 物品。
评估：全库 24,587 候选、屏蔽用户历史、5,744 个测试用户、单一随机种子（42）。
CPU 可复现，全流程约 30 分钟。

---

## 0. TL;DR

**召回层**（全库排序，Recall@50 / HR@10）：

| 方法 | Recall@50 | HR@10 | 说明 |
|---|---|---|---|
| 随机 | 0.20% | — | 50 / 24,587 |
| 热度基线 | 7.45% | 2.86% | 给所有人推 Top-50 热门 |
| 单 query 语义（FAISS） | 4.28% | 1.76% | **低于热度基线** |
| **文本双塔（本文）** | **10.20%** | **4.30%** | 超过 ID 基线 |
| SASRec（ID 基线） | 8.93% | 3.33% | |
| SID 生成式检索 | 8.86% | 3.95% | 打平 SASRec |

**端到端**（全库 → 召回 50 → 重排 → Top-10，分母是全体测试用户）：

| 系统 | HR@10 |
|---|---|
| 单 query 语义 + 重排（v1） | ≈ 2.6% |
| SASRec 单模型 | 3.33% |
| **双塔召回，不重排** | **4.30%** |
| 双塔召回 + 重排 | 4.06% |

**五个结论**：

1. **召回是瓶颈**：单 query 语义召回 4.28%，低于"推热门"的 7.45%。
2. **修召回能翻盘**：训练双塔 → 10.20%，端到端 4.30% 超过 SASRec 的 3.33%。
3. **钱在长尾**：双塔在 tail 上 3.07%（SASRec 0.21%），代价是 head 少 1.5pp。
4. **精排冗余**：受控池上 +8.2pp，真实链路上 0 增益（4.30% → 4.06%）。
5. **生成式是补充路线**：SID 检索 8.86%，打平 SASRec，但没超过双塔；瓶颈是监督量，不是表达力。

## 1. 问题与设定

工业界都在试 LLM 特征，但多数讨论停在"能不能涨点"。我想问一个更窄、可以被证伪的问题：

> **在一个已经有强 ID 协同信号的系统里，语义特征应该放在链路的哪一段？它的增益落在哪类物品上？**

链路两段：

```
物品文本 ──Qwen3-Embedding──> 1024d ──> 召回(Top-50) ──> 重排(Top-10) ──> 展示
                                          ↑
                                    用户历史编码
```

评估口径（全篇统一）：

- 候选：全库 24,587，**屏蔽用户历史**；
- 用户：5,744 个测试用户（按 uid 80/10/10 切分）；
- 对照：**随机 / 热度 / 强基线** 三条线，缺一条就无法判断"涨"是不是真的。

---

## 2. 结论一：召回是瓶颈（4.28% < 热度 7.45%）

| 方法 | Recall@50 |
|---|---|
| 随机 | 0.20% |
| **热度基线** | **7.45%** |
| 单 query 语义 | 4.28% |

热度基线 = 给所有人推同样的 Top-50 热门物品（排除各自历史）。
它之所以高，是因为交互极度头部化：**Top-50 只占 0.2% 的物品，却覆盖了 7.9% 的交互**。

而单 query 语义召回只有 4.28%——**连"推热门"都没过**。
原因很直接：只用最后一个物品做 query、没有任何训练、单路召回。

> 这一步的意义不是"语义不行"，而是**定位**：既然召回低于零智能基线，后面重排做得再好也没用。

---

## 3. 结论二：修召回能翻盘（4.28% → 10.20%）

**结构**：item 塔（1024d 文本 → MLP → 64d，L2 归一化）+ user 塔（历史文本 attention pooling → 64d）。
**损失**：InfoNCE（in-batch 负例）+ **logQ 校正**（抵消热门物品被采样的偏差）。

| 配置 | Recall@50 | HR@10 |
|---|---|---|
| 未训练，last-item 检索 | 4.28% | 1.76% |
| 训练 + last pooling | 7.66% | — |
| **训练 + attention pooling** | **10.20%** | **4.30%** |
| 去掉 logQ 校正 | 3.46% | — |
| 打乱用户历史（负对照） | 3.39% | — |

三点解读：

1. 第一行 4.28% 复现了原来的 FAISS 结果，**说明评估代码是对的**；
2. 训练本身值 +3.4pp（学到更好的度量），attention pooling 再 +2.5pp（会挑历史里的物品）；
3. logQ 校正很关键（去掉后 3.46%）；打乱用户历史后掉到 3.39%，**说明 6.8pp 的增益来自用户侧**，不是物品偏置。

端到端：召回 10.20% → **4.30%**，超过 SASRec 单模型的 3.33%。

---

## 4. 结论三：钱在长尾（tail 3.07% vs 0.21%）

按 target 物品的交互量三等分（同一批测试用户）：

| 方法 | 全体 | tail | mid | head |
|---|---|---|---|---|
| 热度基线 | 7.45% | 0.00% | 0.00% | 22.01% |
| 单 query 语义 | 4.28% | 4.01% | 4.79% | 4.06% |
| SASRec | 8.93% | **0.21%** | 1.01% | **25.19%** |
| **双塔** | **10.20%** | **3.07%** | 3.51% | 23.70% |

三条可以直接读出来的事实：

- **SASRec 几乎只在头部有效**：tail 0.21% vs head 25.19%，差 120 倍；
- **单 query 语义是"平的"**（4.0 / 4.8 / 4.1），因为它压根没用协同信号；
- **双塔用 head 的 −1.5pp，换来 tail 的 +2.9pp（14 倍）**，整体才赢。

> 这就是"语义的价值在长尾"的定量证据，而且不需要任何条件池。
> 头部 23.70% < 25.19% 也说明：纯文本塔在热门物品上仍不如 ID 塔，文本+协同是下一步。

---

## 5. 结论四：精排是冗余的（+8.2pp → 0 增益）

同一个重排器（候选间 self-attention + 可学习门控，`final = prior + g·tanh(sem)`），两种口径：

| 口径 | 结果 | 说明 |
|---|---|---|
| 受控池（1 正 + 100 随机负） | SASRec 0.5144 → LEGR **0.5960**（+8.2pp, p<1e-16） | 打分函数更强 |
| 真实链路（双塔 Top-50 → 重排） | 4.30% → **4.06%** | 端到端无增益 |

两个数不矛盾：**一个测"给定候选集谁排得更准"，一个测"整条系统有没有变好"。**

为什么真实链路上没用：

1. **特征同源**：重排器用文本 PCA，双塔的 item 塔也是文本，信息已被用尽；
2. **训练/测试分布不一致**：训练时 target 被注入候选池，测试时池子是纯召回结果；
3. **缺列表级信号**：没有多样性约束、没有业务规则——而这些才是工业界重排真正值钱的部分。

> 换句话说：**重排需要一个"候选之间会互相影响"的目标，而不是一个更强的打分函数。**

> **术语说明**：本文的这个模型严格说是**精排**（在给定候选集内打分）。工业界所谓的"重排"指精排之后的
> 列表级优化——多样性打散、业务规则、上下文建模（PRM），那部分本文没有做。

---

## 6. 结论五：SID 生成式检索（8.86%，打平 SASRec）

把文本向量离散成 4 级语义 ID，再用自回归模型生成候选：

```
1024d 文本 → RQ-VAE(4 级 × 256 码) → SID(c1,c2,c3,c4)
用户历史 SID 序列(40 token) → 4 层 causal Transformer(0.6M) → 逐码生成
                                    ↓
                        trie 约束的 beam search(50) → 候选物品
```

**SID 质量**：码本使用率 100 / 95.7 / 87.5 / 86.3%，冲突率 3.31%，前缀邻域保持 L1 = 74.2%（随机基线 0.39%）。

**检索效果**：Recall@50 **8.86%**（热度 7.45%、SASRec 8.93%、双塔 10.20%）。

| 关键现象 | 数字 |
|---|---|
| 不加 trie 约束的无效生成率 | **100%**（未训练时）→ 加约束后恒为 0 |
| 约束解码后的平均候选数 | 55.2（beam 50，含同码组展开） |

> 结论：**表达力不是瓶颈，监督量才是**——TIGER 用百万级序列，这里只有 5.7 万。
> 生成式在这个数据规模上是"补充路线"，不是"替代双塔"。

---

## 7. 这意味着什么

1. **语义特征应该投在召回覆盖**，尤其是冷门/新品；不要在精排堆语义特征。
2. **评估必须报三条线**：随机、热度、强基线。少了热度基线，4.28% 会被误读成"有效"。
3. **重排要做"列表级"的事**（多样性、业务约束、上下文建模），不是再训一个更强的打分器。

## 8. 附录 A：四个坑（这部分才是项目真正的过程）

| # | 现象 | 关键数字 | 怎么发现 | 怎么修 |
|---|---|---|---|---|
| 1 | 候选池有捷径 | 负余弦规则 HR@10 **0.9098** | 写了一条"跟最后一个物品最不相似就排前面"的规则 | 换 1 正 + 100 随机负 |
| 2 | 模型没在用用户 | 用户向量置零 0.7028 → **0.7089** | 做一个"去掉用户侧信息"的消融 | 同上 + 真 listwise |
| 3 | 条件指标虚高 | n=246，95% CI ≈ ±6pp | 检查评估覆盖了多少用户 | 全体 5,744 用户评估 |
| 4 | 负对照不归零 | 打乱 target 后 4.6% ≠ 0 | 做负对照，发现异常 | 查出热度基线 7.45% |

**坑 1 的细节**：v1 的候选池是"last item 的 FAISS 近邻"，正例恰好是唯一没被选进来的那个，
所以"越不相似越可能是答案"；而 50 个难负例本身又是由用户 query 生成的，等于把 query 泄露给了模型。

**坑 4 的意义**：如果没有这个负对照，我不会去算热度基线，也就不会发现"4.28% 低于零智能基线"。

详细推导见 [`scripts/v2/README.md`](scripts/v2/README.md)（评估协议）与
[`scripts/v2/sid/README.md`](scripts/v2/sid/README.md)（SID）。

```bash
# 召回：双塔（约 45s）

```

**口径说明**：本文所有跨模型对比都在 5,744 个测试用户上完成。
若用全量 57,439 用户，单 query 语义为 4.32%、SASRec 为 8.48% / HR@10 3.14%，与本文数字略有差异，属正常。

**依赖**：Python 3.11 / PyTorch 2.8（CPU）/ NumPy / FAISS（仅建索引用）。

## 10. 局限

1. 单 seed、未调参；双塔 0.6M 参数、SID 生成器 0.6M 参数，都不是 SOTA。
2. SID 有 3.31% 冲突未消歧（TIGER 用追加 token 解决），这部分物品在生成端不可区分。
3. 冷启动用的是"按交互量分桶"的观测口径，不是真正的 item-holdout 实验。
4. 端到端只测了 HR@10，没有覆盖多样性/覆盖率等体验指标。
